New here? Start here

  
Start in four steps.

  
You need a Mac with 16 GB of memory or more. Everything is typed in Terminal, an app that comes with every Mac.

  
    
    
  1. 1Install extra. Then open Terminal: press Cmd + Space, type Terminal and press Enter.
    2. 
    
  2. 2Type extra and the folder you want to work in, for example: extra ~/Documents/my-app. If the folder does not exist, extra creates it.
    3. 
    
  3. 3In the box at the bottom, write what you want in your own words, for example: make a simple to-do web page. extra writes the files, runs them and fixes errors by itself.
    4. 
    
  4. 4Before it writes a file or runs a command, extra asks. Type y for yes, a for always, n for no. Type /help any time to see every command or ask how something works.
    5. 
  






  
A real run

  
Claude stopped halfway. extra finished it.

  
This is one real run, shown as it happened. The window below is extra's own output, the pictures are the page it finished, and every number was measured.

  

    
1
What Claude left
A currency converter half done: the page, the styles and the conversion work. Getting live exchange rates was still a stub with fixed numbers. Claude left a handoff note (what is done, what is next) and a check script that defines done.

    
2
What extra did
It read the note, tried a free rates API with curl, wrote getRates(), and ran the check. The check failed (no warning when offline), so it read why, fixed one function and ran it again until it passed. Then it updated the note for Claude. 8 steps, 9 minutes 53 seconds, no help.

    
3
How it was checked
The check opens the page in a real browser (headless Chrome) three times: online, offline after one visit, and offline on a first visit. It looks at the status line, its colour, the saved time and the converted amount, and prints what it saw.

How often it works

    
We ran this same task 18 times from the same starting point. 12 runs passed. Each failure had a different cause, and each one is now caught by the program: forgetting the task in long runs, not finding where an error came from, repeating the same command, putting the tool name inside a command, editing the check itself, and stopping while the check still failed. After the last fix, the last 3 runs in a row passed.

    
It is still a small model. Sometimes it cannot find a bug. When that happens, extra does not pretend: it says it stopped with the check still failing and writes that in the note for Claude.

# Leave a handoff note for extra

While you work on a task that takes more than a few steps, keep `.extra/handoff.md` in the project root up to date.
If you hit a usage limit, the user runs `extra continue` in the same folder, and extra reads this note first.

Update the note:
- when you start the task (the goal and your plan),
- after each meaningful step (a file changed, a test run, a decision made),
- right before you stop for any reason.

Keep it short and current. Use this format:

```markdown
# Handoff
## Goal
<what the user wants, in one or two sentences>
## Done
- <finished steps, with the files they touched>
## In progress
- <what you were doing, and the exact next command or edit>
## Next
1. <remaining steps, in order>
## How to test
<the command that shows the task works>
## Notes
- <decisions, gotchas, things not to change>
```

Rules:
- Write facts that a reader with no context can act on. Do not use names you made up during the work.
- Never put secrets (API keys, passwords, tokens) in the note.
- Suggest adding `.extra/` to `.gitignore` unless the user wants the note in the repository.

# Work together with extra

extra is a small local model that solves one problem slowly but thoroughly: it plans, predicts, runs the real code, reads
why it failed, and tries other ways until a check passes. It costs you no tokens while it works. You are faster and
better at judgment. Split the work so that **you never wait for extra**.

## When to delegate
Delegate a piece only when all of these hold:
- It is self-contained: it does not touch the files you are about to edit next.
- It has a check: a command that exits 0 when the piece is done (a test file, a script, `npm run build`, ...).
  If no test exists, write a small one first (that is cheap for you) and include it in the job.
- You can describe it in a few sentences: inputs, outputs, files, constraints.

Good pieces: making failing tests pass, a well-specified function or module, a bug with a reproducing test, porting
code under an existing test suite, edge cases, small tools. Keep design, cross-cutting changes and final integration yourself.

## How to delegate
Run this with the Bash tool and `run_in_background: true` from the project root, then immediately continue with your own work:

```bash
extra run "<task: what to build or fix, the interface, constraints>" --test "<check command>" --files "<a.py,b.py>" --minutes 30
```

Optional: `--prompt "<extra instructions for this job>"` (style, libraries to use or avoid).
extra works in a private copy of the project, so it never collides with your edits. Only one job runs at a time on the
user's Mac; further jobs queue, so do not start more than two.

## While it runs
Do not poll and do not sleep. Keep working on other pieces. You will get a notification when the background command ends.
To peek at progress without waiting: `extra show <id>` (shows the steps it tried so far).
If you finish everything else first, do not wait idle: prepare the next piece, write tests, or review your own work.
If a job runs past its time and you need the piece now, take it over yourself; `extra show <id>` lists what extra
already tried and why it failed, so you do not repeat it.

## When it finishes
The notification output is extra's result (status, test result, changed files, summary). Then:
1. Review: `extra show <id>` prints the diff. Check it like a code review: correctness, scope (only what was asked),
   style, no unrelated changes. Run the check yourself if it matters.
2. Use it: `extra apply <id>`. It copies the changes into the project and merges with your edits to the same files;
   if they overlap, it changes nothing and tells you which files to merge by hand.
3. Or send it back, in the background again, with the concrete reason:
   `extra run --job <id> --feedback "<what is wrong, why, and what you expect instead>"`
   Good feedback names the failing case or the line, not just "wrong". After two send-backs, take it over yourself.

## Keep the user informed
Mention in one line when you hand a piece to extra and when you apply or send back its result.
If you also keep `.extra/handoff.md` (extra-handoff skill), list running job ids there, so `extra continue` knows about them.

What matters here

    
On its own, the small model gets 68.2% on the first try, below the large models. Letting it run its own code, read the real error and try again takes the same model to 83.6%. Nothing about the model changed; only the way it works did.

    
Most of the gain comes in the first three tries. After five tries it barely moves, because extra can only fix what an error shows it. Good tests make extra better.

    
extra trades time for accuracy. It is slower than a large model, but it runs on your computer with no usage limit, so it can keep trying while your main assistant is out of quota.

Modules

  
Small add-ons that change how it works.

  
Each module plugs into the same local model. Turn them on one at a time and keep the ones that help.

  

    
Handoff
FREE
Reads where your last assistant stopped in this folder and continues the same task without starting over.

    
Self-Install
FREE
Installs the packages and downloads the files it needs, after you approve each one with y/n.

    
Plan · Expect · Act
FREE
Before each step it writes what it will do and what it expects to happen, then does exactly that.

    
Run & Retry
PLUS
Runs the code it wrote, reads the actual error or test result, and tries again with that in hand.

    
Another Way
PLUS
When it gets blocked, it lists other approaches and tries the best one before it tells you something can't be done.

    
Honesty Check
FREE
Catches answers that claim work it didn't do, like a file it never saved, and makes it finish the job.

    
Skills
FREE
Built-in expert instructions for design, browser testing, debugging and verifying before saying done — from Anthropic's and the superpowers open-source skills. extra picks the right ones for your request.

    
Safe Edits
FREE
Shows a colored diff and asks before it writes a file or runs a command. It never writes outside your project.

Tips

  
Tips for running extra well.

  

    
Turn on two Ollama settings
In Terminal, run the two lines below, then quit Ollama from the menu bar and open it again. On our Mac, writing got about 32% faster (10.3 → 13.6 tokens a second) and the model used about 1 GB less memory. Answers stay the same.
launchctl setenv OLLAMA_FLASH_ATTENTION 1
launchctl setenv OLLAMA_KV_CACHE_TYPE q8_0

    
Need it faster? Think less
Type /set effort low and /set verify off. extra plans less and stops checking each result, so it is faster but makes more mistakes.

    
Give it a check command
extra fixes what an error shows it. A test or a small script that fails until the job is done makes it much better.

    
Let Claude leave a note
With the extra-handoff skill, Claude keeps a note of the task. Then run extra continue anywhere and press Enter to pick up the newest note.
